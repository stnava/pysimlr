# pysimlr correctness audit — 2026-09-19

Every finding below was reproduced by a script. Ordered by user impact.
Severity: **critical** = reported numbers are wrong; **high** = silently does
nothing; **medium** = comparability / maintenance.

---

## A1 (critical) — the `regression` gradient is not the gradient of the `regression` energy

`simlr.py:598`

```python
if energy_type == "regression": return 2 * (x.t() @ u - v)
```

For `E(V) = ||X - U Vᵀ||²_F` the descent direction is

    -∂E/∂V = 2 (Xᵀ U - V UᵀU)

The shipped expression drops `UᵀU`. It is the correct direction only when
`UᵀU = I`.

**It is never `I` here.** `compute_shared_consensus` returns column-standardised
scores, so on the 3-view case with n=280 training rows:

| consensus | `‖UᵀU − I‖_F` | `diag(UᵀU)` |
|---|---|---|
| newton / svd / pca / ica | 481.5 | [279, 279, 279] |

`UᵀU = (n-1) I`, so the `V` term is under-weighted by **279×** and the direction
reduces to the constant `2 XᵀU`, which does not depend on the current iterate.

Finite differences, `n=60, p=12, k=3`:

| `U` | cos(−fd, shipped) | cos(−fd, corrected) |
|---|---|---|
| `U ~ N(0,1)` (`UᵀU ≈ nI`) | **−0.0045** | +1.0000 |
| `U` orthonormal (`UᵀU = I`) | +1.0000 | +1.0000 |

The shipped direction is **orthogonal** to true descent in the regime the
library actually runs in.

**Consequence.** This is the default `energy_type`, and the one the whole
regression benchmark uses. It explains the symptoms chased earlier in this
repo: energy reduction of ~1e-6 over a whole solve, an objective that looks
"flat", and `lars` appearing to stall. The loop is not descending its
objective; it is iterating a fixed-point map.

## A2 (high) — half the documented `energy_type` values have no gradient at all

`simlr.py:605` ends with `return torch.zeros_like(v)`. Everything not explicitly
handled falls through to a zero gradient:

| `energy_type` | gradient |
|---|---|
| `regression`, `acc`, `logcosh`, `exp`, `gauss`, `kurtosis` | nonzero |
| **`nc`, `normalized_correlation`, `cca`, `pca`, `ica`, `dat`** (no prior) | **identically zero** |

`nc` and `normalized_correlation` have a *documented energy* (`simlr.py:555`)
and a finite-difference gradient of norm 0.134 — the energy is differentiable,
the gradient was simply never written.

**V still moves**, because `simlr_sparseness` retracts every sweep, so nothing
looks wrong from outside:

| `energy_type` | `max‖V_final − V_init‖` | `energy_reduction` |
|---|---|---|
| `regression` | 0.7070 | 3.4e-06 |
| `nc` | 0.6965 | **0.0** |
| `cca` | 0.6965 | **0.0** |

Note how little `regression` adds over a pure no-op: essentially all movement
is the retraction, not the optimiser.

**Consequence for results already reported.** `scripts/unified_real_benchmark.py`
sweeps `losses = ["regression", "acc", "logcosh", "nc"]`. The *best* Diabetes
configuration in the v34 run was `nc + newton` at 0.3868 — a configuration in
which the optimiser provably never runs. That number is PCA initialisation plus
retraction, and must not be reported as an optimisation result.

## A3 (medium) — five mutually inconsistent "orthogonality defect" functionals

`utils.py` exports `orthogonality_defect` (504), `angle_defect` (631),
`invariant_orthogonality_defect` (769), `stiefel_defect` (805),
`mean_orthogonality_defect` (892), each with a gradient twin. A **sixth** is
computed inline in `benchmarks/runner.py` as `‖VᵀV − I‖²_F` and reported as
`Frame_Defect_D`.

Evaluated on one basis:

| basis | `orthogonality_defect` | `angle_defect` | `invariant` | `stiefel_defect` | `mean` |
|---|---|---|---|---|---|
| **disjoint non-negative, unequal column norms** | 0.2267 | 0.0000 | 0.0000 | **35.4682** | 0.0000 |
| orthonormal | 0.0000 | 0.0000 | 0.0000 | 0.0000 | 0.0000 |
| random dense | 0.0672 | 0.0373 | 0.0247 | 56.8886 | 0.0373 |

Spread on pysimlr's *ideal* output — a disjoint non-negative basis — is
**35.47**. `stiefel_defect` scores it 35.47 because it charges unequal column
norms; three others call it perfect.

`simlr`'s energy uses `orthogonality_defect`; the benchmark table reports the
inline sixth. They are not the same number and are compared across models.

This is the same defect nsa_flow consolidated into one `ORTH` registry.

## A4 (medium) — the energy includes an orthogonality term the gradient omits

`simlr.py:825` adds `orth_e = orthogonality_defect(v_sp) * constraint_weight *
orth_weights[i]` to `smooth_energy_fn`, but `smooth_gradient_fn` returns only
`sim_grad + dom_grad`. Energy and gradient are of **different functions**, so
any line search or curvature estimate built from them is inconsistent, and a
stationarity certificate computed from the gradient does not certify the energy.

---

## A5 (confirmed, already fixed upstream) — float32 denormal floor

`clamp_min(1e-300)` on a float32 tensor clamps to `0.0`. Reported from here and
fixed in nsa_flow 3.0.0 (`241beb6`). **pysimlr itself contains no fp32-denormal
literals** — grep for `1e-{40..300}` returns nothing.

---

## Not findings

- Test hygiene is sound: no `test_*.py` without tests, no module-scope
  `set_default_dtype`, no collection-time training loops.
- `torch.manual_seed` in `sklearn.py` is guarded by a user-supplied
  `random_state`, which is the documented contract, not RNG clobbering.

---

## Implications for the redesign

1. A1 must be fixed before any benchmark number is trusted. Every
   `energy_type="regression"` result in the repo is from a non-descent
   iteration.
2. A2 means the loss sweep in the real benchmark is partly vacuous. Either
   implement the missing gradients or refuse the unsupported `energy_type`
   loudly instead of returning zeros.
3. A3/A4 are the centralisation target: one defect registry, one energy, one
   gradient, and a test that the gradient matches the energy it is paired with.
